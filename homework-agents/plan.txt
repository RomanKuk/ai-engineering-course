Step-by-Step Plan

Set up the project and environment.
Create a fresh app inside the homework folder with FastAPI, Streamlit, LangGraph, LangSmith, pandas, and SQLite support. Add environment variables for your model provider and LangSmith.

Explore the dataset first.
Write one small script or notebook to answer the obvious patterns from the README using the real CSV: monthly coffee spend, subscription list, latest Sportlife payment, delivery after 21:00, suspicious merchants, and the credit-payment pattern. This step gives you trusted expected values for later tests.

Load the CSV into SQLite.
Create one transactions table and add indexes on date, category, merchant, and account. SQLite is enough here and keeps queries deterministic and fast.

Build a finance service layer.
Before any agent logic, implement plain Python functions that answer the business questions from SQL. Examples: spending in a time window, top categories by month, merchant last payment, recurring subscriptions, compare periods, estimate month-end balance, suspicious transaction lookup.

Add a conversation-state layer.
Store last resolved category, merchant, time period, and intent per chat session. This is required for follow-up questions and is easy to keep in memory for the demo.

Implement safety and scope rules.
Create a pre-check that detects fraud/dispute wording, out-of-scope investment requests, and unclear requests. Fraud should immediately route to an escalation response instead of normal analysis.

Build the single-agent baseline.
Use one system prompt plus the finance tools. The baseline should be able to choose tools, summarize results, and give actionable advice based only on tool outputs.

Build the crew with at least 3 specialized agents.
A practical split is:

Guardrail/Router agent for scope, fraud, and intent classification.
Analyst agent for tool selection and fact gathering.
Coach agent for final response and actionable recommendations.
If you want, add a deterministic orchestrator node around them in LangGraph, but those three specialized agents satisfy the requirement.
Keep both architectures aligned.
Use the same finance tools, same conversation state, and same response policies in both baseline and crew. This matters a lot for a credible side-by-side comparison.

Instrument everything with LangSmith.
Trace tool calls, final answers, architecture name, and per-agent metadata. For inter-agent overhead, mark internal handoff messages and later compute internal-token-share divided by total-token-share.

Create the golden set.
Prepare at least 15 to 20 tasks across these groups:

Factual spend queries
Savings advice queries
Multi-step analysis queries
Fraud escalation queries
Out-of-scope or ambiguous queries
For each case, store the expected outcome, expected tools, and any key numeric facts.
Implement evaluators.
Use a mix of rule-based and LLM-based checks:
Success rate: judge whether the answer solved the task.
Tool selection accuracy: compare expected tools to actual trace tools.
Groundedness: compare numbers in the answer to numbers returned by tools or recomputed from the database.
Latency, token usage, and cost will come from traces automatically.
Build one shared API endpoint.
Expose one chat endpoint with an architecture parameter set to baseline or crew. That satisfies the “shared endpoint” requirement and makes the UI simple.

Build the Streamlit demo.
Add a text input, submit button, architecture selector, answer panel, trace expander, and an Eval tab that runs the golden set for both modes and shows a comparison table.

Run experiments and write the report.
Your conclusion should be concrete, for example:

Crew is better on multi-step analysis and richer advice.
Baseline is faster and cheaper for simple factual queries.
Crew overhead is only justified when tasks need decomposition, safety routing, or synthesis.
