# Звіт: RAG Scaling Experiment — MS MARCO

## Що вимірювали

Протестовано три retriever'и (numpy brute-force, FAISS HNSW, Hybrid BM25+Dense+RRF) на чотирьох розмірах корпусу: 1K → 10K → 100K → 300K passages з BeIR/msmarco (validation). Embeddings — OpenAI `text-embedding-3-small` (1536d), eval set — 200 запитів, метрики — Recall@1, Recall@10, MRR@10, latency p50/p95/p99, RAM.

## Точка перелому

Критичне падіння Recall@1 у numpy baseline відбулося між **10K → 100K**:

| Corpus | Recall@1 | Recall@10 | p50 latency |
|--------|----------|-----------|-------------|
| 1K     | 0.970    | 1.000     | 0.18 ms     |
| 10K    | 0.880    | 0.995     | 3.39 ms     |
| **100K**   | **0.545**    | **0.955**     | **29.5 ms**     |
| 300K   | 0.385    | 0.820     | 83.2 ms     |

Recall@1 впав на **38%** (0.88 → 0.545) при переході до 100K — перевищення порогу 20%+. Recall@10 залишається відносно стабільним до 100K (1.0 → 0.955), що підтверджує гіпотезу: релевантний документ не зникає з топ-10, а лише сповзає з першої позиції.

## Чому саме там зламалося

При зростанні корпусу з'являється більше семантично близьких, але нерелевантних пасажів — distractors витісняють правильний документ з першої позиції. OpenAI `text-embedding-3-small` дає дуже щільний семантичний простір, тому при 100K+ дистракторів косинусна схожість між релевантним і нерелевантним документом стає мізерно малою. Latency у numpy також стала проблемою: 29ms при 100K і 83ms при 300K — це лінійне O(N) зростання, неприйнятне для production.

## Реалізовані fix'и та результати

**Fix 1: FAISS HNSW** (латентність)

| Corpus | Numpy p50 | HNSW p50 | Покращення |
|--------|-----------|----------|------------|
| 10K    | 3.39 ms   | 0.83 ms  | **-75%**   |
| 100K   | 29.5 ms   | 0.77 ms  | **-97%**   |
| 300K   | 83.2 ms   | 1.58 ms  | **-98%**   |

Recall залишився ідентичним numpy (HNSW з `ef_search=64` дає точний результат на цьому датасеті). HNSW повністю вирішує проблему latency.

**Fix 2: Hybrid BM25+Dense+RRF** (якість) — **спростовує гіпотезу**

Hybrid показав гірший Recall@1 ніж чистий dense на всіх розмірах:

| Corpus | Dense Recall@1 | Hybrid Recall@1 | Δ      |
|--------|----------------|-----------------|--------|
| 1K     | 0.970          | 0.815           | **-16%** |
| 100K   | 0.545          | 0.435           | **-20%** |
| 300K   | 0.385          | 0.315           | **-18%** |

BM25 додає шум, а не сигнал: `text-embedding-3-small` вже охоплює семантику, яку BM25 покриває лексично. RRF-злиття понижує позицію правильного документа. Крім того, latency hybrid'а катастрофічна: 611ms p50 при 300K через O(N) BM25 scoring.

## Рекомендації для production на 1M+

Для корпусу 1M+ рекомендується наступний стек:

1. **FAISS HNSW або Qdrant HNSW** для векторного індексу — sublinear latency (<5ms навіть на 1M+), прийнятний recall.
2. **Відмовитись від BM25 hybrid** при використанні сильних dense-моделей (OpenAI, BGE-large) — він погіршує якість і вбиває latency.
3. **Reranker** (BAAI/bge-reranker-v2-m3 або Cohere Rerank) для відновлення Recall@1 — cross-encoder reranking топ-50 кандидатів дає +10–20% Recall@1 при фіксованій latency (<100ms додатково).
4. **Disk-based індекс** (Qdrant з mmap або pgvector) при 1M+ щоб не тримати 6GB+ embeddings у RAM.
